# How Kiro was used: the truth, file by file

Written 2026-11-23. This page says what happened, not what would look good.

## What Kiro did and what it did not

- The three spec files (requirements.md, design.md, tasks.md), the three steering files (product.md, tech.md, structure.md) and the one hook (run-tests-on-save.json) in .kiro/ were drafted by an AI coding agent as inputs for Kiro. They are in Kiro's formats. They were not generated by Kiro.
- The first engine commit (00830af) was written by an AI coding agent working from those specs. It was not written by Kiro. The commit carries a co-author trailer for that agent, and the author identity on the commit is the repository owner's. The code uses plain JavaScript and node --test, not the TypeScript, vitest and fast-check stack that .kiro/steering/tech.md proposes.
- The landing page, the verified-links file, the deploy script and this submission folder were also prepared by an AI coding agent (task T2964), not by Kiro.
- As of this commit there is no Kiro-authored commit, every checkbox in .kiro/specs/resurrect/tasks.md is still unticked, there is no .kiro/settings/mcp.json (no MCP server was configured), and there are no .kiro/logs transcripts.
- Kiro features that exist in the repository as files: spec-driven development (specs), steering, and one agent hook definition. Kiro features not used: MCP, powers, Kiro CLI or IDE chat transcripts.

NEEDS SAUL before submitting: the hackathon asks for an app built with Kiro. As the repository stands, the engine was built by another agent. To make the claim true, Kiro must implement real work from tasks.md (run the tasks in the Kiro IDE or CLI, commit the result and the transcripts), and this page must then be updated to say exactly what Kiro wrote. Do not submit the sentence "built with Kiro" until that has happened.

## Property tests are hand-rolled, not fast-check

The design calls for fast-check. The repository has no dependencies at all, so the property tests (tests/properties/) use a small seeded random generator (tests/properties/gen.js). A failure prints its seed so it can be replayed. This is property-style testing written without the fast-check library.

## Steering and hook: what they actually did

- .kiro/steering/product.md holds the honesty rules (no invented fields, a dated source for every dead API, the disclaimer, no performance figures). Those rules are enforced by tests (tests/site.test.js, tests/landing.test.js), written by the same agent that read the steering file. The steering file did not make Kiro obey anything, because Kiro has not run in this repository yet.
- .kiro/hooks/run-tests-on-save.json is defined to run npm test after a source or test file is saved. It has not been seen firing in Kiro.

## What the specs did change

The specs fixed the shape of the work: which dead APIs are in scope and why each is dated and sourced, the rule that a mapping may only target a live endpoint in the catalog snapshot, the null-with-reason rule for fields, and the numbered correctness properties that became tests. That is real, and it is the part of the process this repository can show.
